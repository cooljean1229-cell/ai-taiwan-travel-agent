# PRD｜旅行社獲客與智慧行程推薦網站

**版本：**1.0｜**狀態：**規劃稿，待產品/旅行社負責人確認範圍後實作  
**建立日期：**2026-11-27｜**內容依據：**CCI、SIPOC、2026-11-23 至 2026-11-29 週報及 `research/travel-data.json`。  
**技術限制：**第一版僅使用 HTML、CSS、JavaScript；不加入 Supabase，不要求伺服器端秘密或第三方 API。

## 1. 目標

1. 以每週旅遊情報吸引親子、情侶、熟齡旅客，提供清楚的主題入口。
2. 讓旅客以旅遊對象、每人預算、天數、風格快速縮小選擇，閱讀推薦理由及資料限制。
3. 將有意願者引導至旅行社諮詢；第一版不收集或傳送聯絡個資。
4. 所有可驗證內容均能追溯來源及查詢日期；資料過期、未知或有衝突時不以猜測補足。

第一版不承諾提升轉換率或營收；若示範任何成效數字或旅客案例，須標示「模擬資料」。

## 2. 使用者

- **親子旅客：**希望依同行對象和興趣找活動；兒童年齡限制、場地設施及步行條件若無來源，一律待確認。
- **情侶旅客：**想依節慶、藝文、戶外等風格找候選；活動日期、時段、交通仍以最新官方資料為準。
- **熟齡旅客：**希望按活動節奏、興趣及同行需求評估；不可因熟齡標籤推定無障礙、接駁或適合個別行動能力。
- **旅行社內容維護者（內部）：**以靜態資料檔更新活動、方案、來源、查詢日期及狀態；第一版不提供後台介面。

## 3. 頁面與主要內容

### 3.1 首頁／本週旅遊情報

- 專案/旅行社識別、清楚主標與「依需求找行程」主要行動按鈕。
- 本週情報摘要與親子、情侶、熟齡三個入口。
- 顯示週報期間、資料查詢日期及資料更新提醒；活動內容不可暗示為旅行社可售產品。
- 顯示本期已結束或待確認項目的明確狀態，避免出現在有效推薦主列表。

### 3.2 找行程／偏好表單

- 欄位：旅遊對象、每人預算上下限、旅遊天數、旅遊風格。
- 清楚顯示預算單位及包含範圍；支援空值/尚未決定，提供欄位說明及驗證錯誤。
- 主要操作「查看推薦」；次要操作「清除條件」。
- 不要求姓名、電話、Email、生日或精確健康資訊；不保存表單內容。

### 3.3 推薦結果／比較

- 顯示結果數、排序依據、每筆卡片與條件比對清單。
- 卡片顯示活動/方案名稱、地區、內容摘要、已知日期、價格與天數資料狀態、客群/風格吻合理由、官方描述或研究判斷、來源/查詢日期、待確認事項。
- 支援調整條件、重新比對、回到週報及透過既有公開聯絡方式諮詢（聯絡網址/方式由旅行社提供；未提供時按鈕不顯示或以「聯絡方式待確認」呈現，不造出網址）。
- 若未找到符合方案，顯示空狀態與可行下一步，詳見「找不到方案」。

### 3.4 情報/活動詳情（可用頁面區塊或獨立頁）

- 完整介紹、來源連結、查詢日期、有效期間、活動狀態與研究判斷標示。
- 待確認資料以可見提示說明尚缺何資訊；過期資料顯示結束日期並排除推薦。

### 3.5 隱私與使用說明

- 說明偏好僅在本次頁面操作中用於篩選，第一版不送至後端、不保存。
- 說明活動情報不是可訂購/庫存保證，報價、時段、報名與交通須向官方或旅行社確認。
- 若之後加入聯絡表單，須另行定義蒐集目的、必要欄位、保存期限及告知內容；此項不在第一版。

## 4. 功能需求

### 4.1 偏好選擇

- 旅遊對象：親子、情侶、熟齡旅客，可多選；至少允許「尚未決定」。
- 預算：每人新臺幣總預算（NT$/人），以最低/最高範圍輸入；不可留有未說明的「總價」或「團費」含義。
- 預算包含範圍：產品預設定義為「單一旅客整趟行程預算」。交通、住宿、餐食、門票及其他項目若價格資料未明列，旁註「包含範圍待確認」；選項不得使旅客誤認已含。
- 天數：整趟旅遊日數（天）。資料只有活動期間而非完整行程時，標示「行程天數待確認」。
- 風格：根據資料主題的多選項及「不限」。不可把未提供風格當成負向條件。
- 所有輸入支援鍵盤操作、標籤與錯誤訊息；範圍上下限不合理時提示修正。

### 4.2 推薦結果呈現

- 每項推薦必須講出哪個使用者條件吻合及對應資料欄位；不得用無來源評分、人氣或「最佳」作理由。
- 官方描述與研究判斷使用不同文字標籤。
- 每筆可驗證內容提供來源名稱、頁面標題、網址與查詢日期（YYYY-MM-DD）。
- 價格、行程天數、交通、名額、報名、開放時段缺失時明確顯示「待確認」；不呈現虛構價格或庫存。
- 來源更新日超過維護者設定的檢查期限時標示「資料可能過期，出發前請重新確認」；期限尚未由負責人核定前，呈現查詢日期及「新鮮度門檻待確認」，不自行聲稱資料仍有效。
- 任何範例推薦或虛構使用者須顯著標示「模擬資料」。

## 5. 推薦邏輯

推薦採可解釋的規則式篩選/排序，第一版在瀏覽器 JavaScript 執行，不使用模型推測，不計算虛構評分。

1. **資料有效性閘門：**排除已過結束日期的活動。`待確認` 記錄不列為正式推薦，只可在獨立「資料待確認」區塊顯示，並附上缺少的確認事項。資料狀態或日期缺漏時視為未知，預設不推薦。
2. **硬性條件篩選：**只以已知且可比較的資料檢查日期、價格和天數。使用者設定預算而資料沒有價格，結果標為「價格未知」，不得算符合預算；使用者要求天數而資料沒有完整行程天數，同理標為「天數未知」。可在候選區保留未知方案供諮詢，但不能放入「符合全部條件」區。
3. **相關性排序：**在有效候選中，依有依據的旅遊對象、風格及地區等已填偏好排列；官方直接描述可作較強匹配依據，研究判斷明確標籤且弱化為參考。不要創造精確百分比或星等。
4. **理由組成：**逐條列出「符合：客群/風格/日期」及「尚未確認：價格/天數/報名/交通」；理由須對應資料欄位，不得擴大來源含義。
5. **無符合方案：**明確告知目前資料找不到符合全部條件的方案，提示可放寬的條件（例如增加預算上限、改選風格、天數選不限）或洽詢旅行社協助；不可偷偷放入過期/待確認資料，也不可承諾旅行社一定有替代商品。
6. **價格單位與可比性：**使用者預算統一為 NT$/人/整趟；只有資料明載相同計價基礎及包含範圍的報價才可比較。團體總價、兒童價、單晚價或未標清包含範圍均不直接換算成每人整趟價格，狀態標成「計價基礎待確認」。本期沒有來源價格，所有方案價格顯示「待確認」。

## 7. 響應式版型與可用性

- **手機優先：**單欄表單與卡片；窄螢幕不需水平捲動；主要按鈕全寬或易於觸控。
- **平板：**內容置中且限制閱讀寬度；可用雙欄卡片，表單順序仍按對象、預算、天數、風格。
- **桌面：**主內容使用清晰網格；表單與結果可並列，但小型視窗自動堆疊。
- 斷點由實作時依內容定義並記錄；不得以裝置型號假定所有寬度。
- 使用語意化標題、表單標籤、鍵盤焦點、明確錯誤訊息及足夠對比；狀態不只依顏色辨識。
- 來源與待確認提示在手機上仍可閱讀、連結可操作；不得藏在 hover-only 元素中。
- 支援窄螢幕、長活動名稱及無結果狀態，不讓內容重疊或截斷關鍵警示。

## 8. 內容更新與資料過期處理

- 靜態資料由旅行社內容維護者更新；每次更新同步檢查名稱、日期、狀態、來源網址、查詢日期和待確認事項。
- 活動結束日早於目前日期即標為已結束並自推薦排除；缺少日期/時區或活動多場次難以判斷時列待確認，人工確認後再改狀態。
- 來源查詢日期超過核定的新鮮度期限即顯示「資料可能過期」並暫停其即時可參加宣稱；新鮮度期限目前未定，負責人待確認。
- 來源內容矛盾時保留原始來源連結，標待確認並暫停正式推薦，不由網站自行裁決。例：花蓮鯉魚潭水岸光影節季節描述與日期不一致。
- 過期項目可保留在情報歷史/檔案頁並明示已結束；不可混在可參加推薦中。例：2026 台中國際花毯節（2026-10-31 至 2026-11-22，來源查詢日期 2026-11-27）。

## 9. 非功能與範圍限制

- 無後端、無帳號、無資料庫、無 Supabase、無付款/預訂/庫存功能。
- 靜態內容以 HTML 可讀、JavaScript 增強；停用腳本時至少仍可讀取本週情報與聯絡說明。
- 不在前端放 API Key、密碼、存取權杖；第一版不需任何憑證。
- 偏好不傳輸、不持久保存；如加入分析或表單，須另行評估告知與個資規範。
- 外部事實均附可追溯來源和查詢日期；無法確認者明示「待確認」及缺少事項；虛構示例明示「模擬資料」。

## 10. 驗收條件

### 產品功能

- [ ] 首頁提供本週情報與親子、情侶、熟齡入口，並顯示報導期間及查詢日期。
- [ ] 旅客可設定旅遊對象、每人預算、天數及風格；可選不限/尚未決定，表單有標籤和輸入錯誤提示。
- [ ] 預算單位清楚顯示 NT$/人/整趟；包含範圍未知時明示待確認。
- [ ] 推薦結果逐條說明條件吻合與未知欄位；不使用無來源的星等、評分、人氣或成效數據。
- [ ] 沒有符合方案時呈現空狀態、可調整條件與諮詢提示，不用過期或待確認資料偽裝為有效結果。
- [ ] 預設週報資料無價格與完整行程天數時，畫面顯示「價格待確認」及「行程天數待確認」，不稱預算/天數吻合。
- [ ] 活動已過期時從有效推薦排除；待確認項目有明確狀態和缺少事項；來源日期過舊時提示重查。

### 內容與可信度

- [ ] 每一筆可驗證外部事實均顯示來源名稱、頁面標題、網址和查詢日期。
- [ ] 官方描述和研究判斷有不同標籤，推薦理由沒有超出來源支持範圍。
- [ ] 花蓮鯉魚潭水岸光影節按待確認處理；2026 台中國際花毯節按已結束處理。
- [ ] 未確認的票價、交通班次、報名、時段、無障礙、活動場次均不臆測。
- [ ] 所有虛構旅客、偏好、價格、庫存、評分或推薦案例在可見處標「模擬資料」。

### 技術、個資及版型

- [ ] 第一版檔案只使用 HTML、CSS、JavaScript，未加入 Supabase 或未授權後端服務。
- [ ] 前端程式與 Git 內無密鑰、權杖或真實憑證。
- [ ] 第一版不收集或傳送個資，表單偏好不持久化。
- [ ] 手機、平板和桌面均可讀取表單、結果、來源、待確認狀態與無結果畫面；沒有橫向溢位或關鍵文字截斷。
- [ ] 鍵盤可操作、欄位標籤清楚、焦點可見、錯誤可讀，狀態不只透過顏色表示。

**驗收紀錄：**本文件僅定義驗收條件，網站尚未依此實作或複驗；實際驗收須由驗收員填寫日期、版本、證據及通過/不通過/待確認結果。

## 11. 待確認事項

- 旅行社正式名稱、品牌視覺、公開聯絡方式與諮詢承接流程。
- 預算是否採「單一旅客整趟」作正式商業口徑，以及兒童、團體和單房差價格的呈現政策；本 PRD 暫定 NT$/人/整趟供偏好篩選使用。
- 旅行社實際商品、可售地區、價格、完整天數及適用期限；目前週報只有活動情報，不能等同商品庫。
- 來源重查的新鮮度期限、資料維護負責人與更新頻率。
- 是否需要未來聯絡表單/分析工具；若需要，另立需求並完成個資目的、欄位、告知和保存期限確認。
